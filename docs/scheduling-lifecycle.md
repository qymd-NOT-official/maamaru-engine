# 安排的归属与取消

安排的创建、执行和取消必须使用同一份归属。不要通过清文件或扩大按钮范围来代替取消。

## 两个操作的范围

| 操作 | 取消什么 | 保留什么 |
| --- | --- | --- |
| 关闭远征安排 | 循环排班授权、待派的独立班次及今日安排带出的待派班次；停止正在准备的对应派遣 | 日课、其他玩法、等待中的玩法；已确认出发的远征 |
| 停止今日安排 | 当前这份安排的时段、正在执行的子任务、等待续跑及它创建的远征 | 手动任务、独立远征、其他安排、已完成记录 |
| 移除单班远征 | 这班的授权、排队状态和对应派遣准备 | 其他班次及玩法 |

## 数据的职责

- `day_conductor.json` 中的 `plan_id` 是一份今日安排的身份；`cancelled_at` 是明确撤销授权，和流程失败、暂停、未启用不同。
- 由安排创建的远征记录和调度状态携带同一个 `plan_id`。手动采纳的远征没有这个字段；修改已有班次必须保留原归属。
- 运行参数和等待续跑记录传递 `plan_id`。执行器只公开取消所需的 `plan_id / slot_key / scheduled`，不拿脚本类型猜归属。
- 玩家取消后，时段和班次进入 `cancelled` 终态。旧执行结果保留在记录与备份中，不把未知结果标作完成。
- `expedition_takeover.json` 是当前有效等待班次的投影，不是授权来源。取消后重算它，不能把其他班次的小旗一并清空。

`panel/plan_control.py` 是取消的业务入口。HTTP 接口只做输入校验和调用；调度器只执行仍获授权的班次。巡检与控制操作共用 `scheduler.CONTROL_LOCK`，今日安排还使用 `day_conductor._LOCK`，锁顺序为今日安排 → 远征控制 → 单班选择。

停止今日安排先持久化撤销，再定向取消续跑和派遣。即使后续文件写入失败，调度器也不能仅凭残留子班恢复执行。等待点在取消后迟到写入时，沿用已有 root 的取消记录阻止恢复。

## 兼容与重新开工

旧版记录不强行补归属：明确保存过子班键的旧安排可以按该证据取消；没有证据的远征保留为独立安排，通过关闭远征或移除单班处理。已有文件格式仍可读取，写回保留备份。

重新开工是新的明确授权，生成新的 `plan_id`。已取消的同一时刻可以重新安排；已确认完成的相同时段与派遣仍保留防重约束。修改一份未取消的安排继续使用原身份。

只有创建安排或玩家启用班次的入口可以重新授权取消过的同键班次（`authorize_expeditions`）；普通巡检不得因为看见残留选择，就把 `cancelled` 改回待派。

回归重点见 `tests/test_plan_ownership.py`、`tests/test_today_stop.py`：范围隔离、等待点迟到、写入失败、进程重启、旧数据兼容及巡检与取消同时发生。
