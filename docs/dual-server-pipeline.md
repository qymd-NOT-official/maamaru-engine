# 双服玩法流水线设计

> 目标：国服、日服共用同一套玩法流程。玩法流程写成与服务器无关的「流程单」，
> 服务器差异全部收进可替换的「素材包」和「设备适配器」。
>
> 前提共识（老大 2026-10-22 拍板的方向）：游戏机制两个服是一样的——点出阵、
> 点活动、收远征，这些顺风路走固定流程；弹窗、翻车、收拾残局严格来说不属于
> 流程，是引擎层的职责，流程单里不该出现。

## 一、为什么是现在

- MAA 已拆完，画面、识别、点击全在自家代码里，改造没有中间商。
- 日服平行栈已存在且数据层基本完工（见「四、现状盘点」），缺的是玩法层。
- 国服 24 个玩法（`touken/flows/`）全部直连 `self.device` 的像素语义，
  日服只有 `jp_sally.py` 一个平行实现。每加一个日服玩法就抄一遍国服，
  两边会越差越远——要么现在收拢，要么永远收不拢。

## 二、核心命题

刀剑乱舞的玩法逻辑（状态机、判断分支、安全规则）与服务器无关；
与服务器有关的只有三类东西：

| 差异 | 国服 | 日服 |
|---|---|---|
| 画面素材 | 中文 UI 模板 + 中文 OCR 词 | 日语 UI 模板 + 日语 OCR 词 |
| 运行载体 | MuMu 模拟器（ADB，1280×720 像素帧） | DMM 页游窗口（CDP 取帧，尺寸可变） |
| 数据来源 | 客户端本地数据（youzu 事件流） | 浏览器连接记录（JSON） |

数据层已解耦完毕（`TeamSnapshot` 契约、账房事件格式双服一致），
所以本设计只处理前两类：**把「画面素材 + 运行载体」从玩法代码里剥出去**。

## 三、目标架构

```
┌─────────────────────────────────────────────┐
│ 流程单（pipeline DSL，与服务器无关）           │
│   「等地标:按钮/出阵」「认到就点:按钮/出阵」     │
│   「安全出阵(部队二, 重伤停)」「回本丸」        │
├─────────────────────────────────────────────┤
│ 流程引擎（flow_engine 扶正）                  │
│   逐步执行 / 条件跳转 / 重试 / 成绩单          │
│   引擎级安全网：弹窗即停、翻车智能收拾残局      │
├──────────────┬──────────────────────────────┤
│ 内置积木      │ 素材包 ServerPack             │
│ （代码写死，  │ 逻辑名 → 具体素材的绑定表：     │
│  不可绕过）   │ 模板路径 / OCR 词 / ROI /      │
│  安全出阵链   │ 界面名表 / 坐标                │
│  弹窗扫地     │ cn 包 ←→ jp 包                │
│  回本丸       │                              │
├──────────────┴──────────────────────────────┤
│ 设备窄接口 GameDevice                         │
│   screenshot() / click(p) / swipe(...)       │
│   template_match(逻辑名) / ocr(逻辑名)        │
│ DeviceAdapter（国服）  BrowserAdapter（日服）  │
├─────────────────────────────────────────────┤
│ 数据通道（已解耦，本设计不动）                  │
│   youzu 事件流 ｜ 日服 JSON 通道              │
│   → 统一 TeamSnapshot / 账房事件              │
└─────────────────────────────────────────────┘
```

### 3.1 设备窄接口

`jp_sally.py:78-80` 已实证窄接口可行（只要 `screenshot()` + 点击
就能跑玩法）。正式化为协议（`touken/game_device.py` 的 `GameDevice`）：

- `screenshot()` → 帧（device-native：国服 numpy BGR，日服 PIL RGB，
  尺寸以设备自报为准）
- `click(point)` / `swipe(...)` —— 坐标用**基准分辨率像素空间**
  （int 像素）：国服基准 = 实际 1280×720（恒等，零改动）；日服基准 =
  标定锁存分辨率，DMM 页面内容固定宽度，窗口变矮只是视口裁剪，内容
  坐标在「宽度归一化到基准宽」的空间里不变。不采用 0~1 归一化坐标：
  视口高度变化时归一化 y 会漂（2026-10-12 事故），基准像素锚死在内容上
- `template_match(...)` / `ocr(...)` —— 识别能力从 DeviceAdapter 内建
  方法上移到接口，操作设备最近一次 screenshot 的缓存帧

国服 `DeviceAdapter` 只补一个 `base_size` 即结构性满足协议；日服侧
`JpGameDevice`（`touken/jp_game_device.py`）组合 `JpBrowser`，负责
基准像素 ↔ 视口归一化的换算（换算与视口熔断收在 JpBrowser 内）。

### 3.2 素材包 ServerPack

一个服务器一个包，包内是「逻辑名 → 具体素材」的绑定表：

- 模板：`menu/出阵` → 国服 `image/menu/出阵.png` ｜ 日服 `image/jp/menu/出撃.png`
- OCR 词：`界面/本丸` → 「本丸」｜「本丸」（日语同字形）或对应日语词
- ROI/坐标：逻辑区域名 → 归一化坐标
- 界面名表：导航目标「本丸」「出阵」→ 各服导航路径

模板加载入口已集中（`device_adapter.py:437` 和 `:464` 两处），
改造成本低。日服模板目录 `resource/base/image/jp/` 已存在，直接当 jp 包的家。

**模板制作纪律不变**（AGENTS.md 红线）：模板必须从该服实际运行的截图通道
取样，同分辨率同颜色语义，不为不同通道维护两套模板。

### 3.3 流程单

以现有 flow_engine 的 DSL 为基础（它已经是对的形状）：

- 步骤里只准写**逻辑名**，不准出现像素坐标、具体文字、服务器专属路径；
- `click_point`（盲点坐标）这种逃生舱保留，但官方流程单里禁用，
  只留给流程工坊的用户私货；
- 现存步骤类型基本够用：等地标 / 认一下 / 认到就点 / 滑动 / 点安全区 /
  去界面 / 条件跳转 / 内置积木。

### 3.4 内置积木：安全与收拾残局是引擎的事

这层的规则是「流程单写顺风路，妖魔鬼怪引擎挡」：

- **安全出阵链**（选队验证→伤势检查→刀装处理→重伤拦截→二次确认）
  继续是写死的内置积木，任何流程单、任何服都不准拿裸 click 手搓出阵确认
  （现有红线，`flow_engine.py:601-603`）。伤势数据经 `team_state_reader`
  注入缝走——日服换 `jp_party` 阅读器即可复用整条链的安全语义
  （`team_state_reader.py:8-47`）。
- **翻车收拾残局**（v1.4.0 刚统一的智能处置：出错→跳过这步→尝试回本丸→
  成功则继续下一步）上提到引擎层当默认失败策略，替换现在每步手配的
  `on_fail`——流程单作者不需要也不应该决定翻车怎么办。
- **弹窗**维持「弹窗即停、只点认得出的画面」原则（jp_sally 同款），
  弹窗图鉴按服积累，进各服素材包。

### 3.5 保密红线（不变）

日服数据通道的监听器、解密器永不进主仓。若需抽离，面很小：
`jp_listener.py` + `data/jp_endpoints.json` + panel 里 5 个 jp-listener API。
netlog 解析器是通用诊断工具，留在仓内。对外措辞继续低调，
只说「数据同步」「连接」。

## 四、现状盘点（基线：refactor/bye-maa @ v1.4.0）

| 层 | 已有 | 缺口 |
|---|---|---|
| 数据 | TeamSnapshot 双服契约、账房事件格式一致、jp 存储隔离、team_state_reader 注入缝 | 无（完工） |
| 面板 | `?server=jp` 整套 UI 隔离、脚本按服注册、启动器双入口 | 配置加 server 维度（注意 `_fill_missing_config_keys` 老用户补键，异去事故教训） |
| 识别 | OCR 引擎双服共用、jp 模板目录已隔离 | 统一「逻辑名→素材」绑定层；cn_ocr 词表写死中文 |
| 设备 | JpBrowser 归一化点击+CDP 取帧、窄接口实证 | 统一 GameDevice 协议；JpBrowser 补识别能力；1280×720 写死点（`flow_engine.py:30`、`roi_registry.py`、各 flows 帧形状断言） |
| 流程引擎 | DSL 形状已对、内置积木机制已存在、官方流程已可展品化 | 像素坐标→归一化；模板白名单→逻辑名；翻车策略上提引擎 |
| 玩法 | 国服 24 个 flows 全功能；日服 jp_sally 样本 | **24 个玩法的流程单化移植，主要成本在这里** |

## 五、迁移路线

每个阶段独立可交付、可验证，不许跨阶段摊大饼。

- **阶段 0：设备窄接口统一。** 定义 GameDevice 协议；国服 DeviceAdapter
  加归一化适配壳；JpBrowser 补识别能力。验证：国服全量测试不裂 +
  jp_sally 改走新接口后行为不变。工作量：中。
- **阶段 1：流程引擎双服化。** 坐标归一化、模板/OCR 走素材包逻辑名、
  引擎级翻车收拾。验证：现有官方流程在国服表现逐条不变。工作量：中。
- **阶段 2：试点移植一个玩法。** 首选远征或手入（循环类、状态浅、收益高）。
  产出「一份流程单，两个服都能跑」的实证。验证：国服远征流程单化后
  行为对齐 + 日服同流程单跑通。工作量：中（含日服模板采集标定）。
- **阶段 3：逐个吃掉剩余玩法。** 按使用频率排优先级；复杂状态机
  （炼糖、刷花、合战场）放最后。每移植一个，国服该玩法的旧手写流程
  才准退役。

## 六、验证策略

- 流程单化前后行为对齐：同一账号同一状态，新旧实现的日志序列逐步对得上。
- 日服新模板一律从 JpBrowser 实际运行帧裁剪（截图同源纪律）。
- 每个阶段过全量 pytest + 前端测试；涉及配置结构变化的配迁移测试。
- 安全链任何改动按重伤拦截红线做专项验证。

## 七、明确不做

- 不做「通用游戏自动化框架」——只服务刀剑乱舞这两个服，不过度抽象。
- 不在流程单 DSL 里加图灵完备的东西（变量、算术、循环体）——
  分支只有条件跳转，复杂逻辑进内置积木用代码写。
- 不动数据层——它已经解耦完毕。
- 不为省事把日服监听器/解密器任何形式的代码或样本带进主仓。
